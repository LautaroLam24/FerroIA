## Decisiones vigentes

- SDD con OpenSpec: nada se implementa sin change aprobado
- Ventas/entradas de stock: siempre $transaction con validación adentro (409 si no alcanza)
- Baja lógica de productos Y usuarios (`deletedAt`); movimientos inmutables
- Gestión de usuarios: `email` único global (no reutilizable tras una baja), password policy mínima (>=8 chars, letra+numero), `BCRYPT_ROUNDS` vía env, `passwordHash` nunca en respuestas (proyección `select`)
- IA: el LLM nunca decide reposición ni modifica stock; solo redacta sobre cálculos hechos por código. Tampoco confirma órdenes de compra ni las crea confirmadas: la tool del asistente (`crear_borrador_orden`) solo tiene alcance para crear `OrdenCompra` en `BORRADOR` vía `POST /api/purchase-orders/assistant`; confirmar/cancelar viven en `PATCH` con `@Roles(ADMIN)` que la tool ni conoce
- Autenticación de tools del asistente hacia el backend: se reenvía el JWT del usuario humano de la conversación (nunca una identidad de servicio propia), para que la tool quede sujeta al mismo `JwtAuthGuard`+`RolesGuard` que un request manual
- OBS docentes obligatorias: (1) sincronizar ChromaDB ante ABM de productos (eventos NestJS); (2) memoria del chatbot con windowing/summarization de tokens; (3) asistente con function calling para BORRADORES de orden de compra (confirmación humana, no modifica stock) — las tres implementadas
- Ruteo: Claude Code = auth, productos, stock, chatbot, semántica, purchase-orders; OpenCode = usuarios, catálogo, filtros, dashboard, design-system, layout-navegacion, pantallas-crud, stock-y-dashboard
- Navegación frontend por estado (sin react-router, ratificado en `layout-navegacion`): los ítems viven en `frontend/src/navigation/navigation.ts` como única fuente (`id` = valor de `AdminView`, `roles` por ítem) y se filtran con `visibleNavItems(role)` desde el estado de sesión existente; "UI showcase" no se expone en el menú de la app pero queda registrada como vista (requirement del design-system)
- Convención `400` vs `404`: `404` es solo para el `:id` de la URL que no existe; una referencia inválida dentro del body (p. ej. `categoryId`/`supplierId`/`proveedorId`/`productoId` inexistente) es `400` (validación de payload), no `404`. Aplica a todo endpoint que reciba FKs en el body
- Patrón de concurrencia para escrituras de stock (venta, y a futuro reposición CU10): `updateMany` condicional (`where: {stock: {gte: cantidad}, deletedAt: null}`) dentro de `$transaction` interactiva, con `count===0` desambiguado por un `findUnique` de diagnóstico posterior (nunca antes de escribir). Evita `SELECT FOR UPDATE`/raw SQL; se apoya en que Postgres bajo `READ COMMITTED` reevalúa el `WHERE` de un `UPDATE` contra el valor ya confirmado tras esperar el lock de fila — no hace falta `SERIALIZABLE`. Reusar este patrón para cualquier decremento con invariante de negocio (nunca stock negativo)
- Prisma pineado en `6.19.3` (no v7): v7 cambia a un generador experimental (`prisma-client`, salida a `generated/`, `prisma.config.ts`) y su `prisma init` auto-instala paquetes de skills de terceros en `.claude/skills` — rompe la convención de skills propia del repo
- E2E con `maxWorkers: 1` en `backend/test/jest-e2e.json`: las suites comparten la misma DB de dev y las assertions absolutas globales eran flakies con suites en paralelo; los tests e2e nuevos deben acotar assertions a datos propios (prefijos únicos) y no asumir estado global
- DB local de desarrollo: `docker-compose.yml` en la raíz (postgres:16, puerto 5432, user/pass `postgres`, db `ferreteria`, volumen `ferreteria_db_data`) reemplaza al `docker run` manual — pero el contenedor manual sigue siendo el que corre hoy en este entorno (no migrado a propósito, ver Deuda: la prueba de instalación limpia con compose queda para justo antes de la entrega)
- Búsqueda semántica (CU10) reusa el mismo proceso Python de `chatbot` (CU09) en vez de un microservicio aparte — comparten `CHATBOT_URL`/`CHATBOT_TIMEOUT_MS` y el modelo de embeddings ya cargado (`sentence-transformers/all-MiniLM-L6-v2`). El índice (`products_catalog`) nunca es la fuente de verdad de qué mostrar: `GET /api/products/semantic` siempre re-filtra los ids contra Postgres (`deletedAt: null`) antes de responder
- Reposición (CU10): cantidad sugerida = `max(ceil(consumoPromedioDiario * RESTOCK_LEAD_DAYS), stockMin - stock, 1)`, con `RESTOCK_PERIOD_DAYS`/`RESTOCK_LEAD_DAYS` configurables por env (defaults 30/15). El LLM solo redacta el resumen del cálculo ya hecho; si falla, hay fallback determinístico sin LLM — la sugerencia nunca depende de que el LLM esté disponible
- `chat.py` (chatbot) ahora hace tool-calling condicional: solo bindea la tool `crear_borrador_orden` al LLM cuando hay datos reales de `POST /api/restock/suggest` disponibles (heurístico de palabras clave para no llamar a ese endpoint en cada mensaje). Sin esos datos reales, el LLM no tiene ids para copiar y no puede invocar la tool — evita que invente `proveedorId`/`productoId`
- Frontend sin `jest-dom` instalado: en tests usar `toBeTruthy()`/`queryByText(...).toBeNull()` en vez de `toBeInTheDocument()` (falla con "Invalid Chai property")
- Accesible names en tests frontend: un `FormField` con `required` agrega un `*` (aria-hidden) al label → el nombre accesible del control es "Nombre _" y NO matchea `getByLabelText('Nombre')` exacto; usar regex anclado (`/^Nombre/`, y para Stock vs "Stock mínimo" usar `/^Stock\s_\*?$/`). Un `Button`con`loading`incluye el spinner con`aria-label="Cargando"` en el nombre accesible ("CargandoConfirmar") → matchear botones en loading con regex (`/Confirmar/`)
- El servicio Python (`chatbot/api.py`) en dev DEBE levantarse con `uvicorn api:app --reload` (o equivalente) — sin `--reload` no recarga al editar código, y un proceso viejo corriendo responde 404 en rutas nuevas sin ningún error obvio de por qué. Si algo del lado Python "no aparece", primero verificar que el proceso corriendo sea posterior a la última edición
- Criterio Toast vs. error de campo (frontend, ratificado en `pulido-accesibilidad`): si `resolveFormError` devuelve `fieldErrors` (error asociable a un campo: 400 `details`, 409 duplicado) se muestra dentro del formulario, nunca además como Toast; si devuelve `global` (no asociable a un campo: red, error inesperado) se notifica con `Toast` de error. Aplica a toda acción nueva de crear/editar/borrar
- Migraciones Prisma en este entorno (Windows sin TTY): `prisma migrate dev` no corre interactivo → generar el SQL con `prisma migrate diff --from-url <DATABASE_URL> --to-schema-datamodel prisma/schema.prisma --script`, escribirlo a mano en `prisma/migrations/<timestamp>_<nombre>/migration.sql`, aplicar con `prisma migrate deploy`. Reusar siempre este flujo para cambios de schema (usado en `gestion-productos`, `busqueda-semantica` y `ordenes-compra-borrador`)
- Secretos críticos (JWT_SECRET y futuros análogos): fail-fast al bootstrap si faltan, nunca default silencioso a `""`/valor débil (ver `backend/src/auth/jwt-secret.util.ts`). Reusar este patrón para cualquier secreto nuevo del que dependa auth/integridad
- Docker Desktop en este entorno Windows no arranca solo: si `test:e2e` cuelga en `beforeAll` (timeout, no error de código), lo primero a chequear es `docker ps` / puerto 5432 antes de sospechar del código — el contenedor `ferreteria-db` no tiene restart automático del daemon
- Tool-calling multi-turn con Groq (`chat.py responder()`): en la llamada de seguimiento que redacta la respuesta final después de ejecutar un `ToolMessage`, hay que volver a bindear las mismas tools con `llm.bind_tools(...)` aunque no se vaya a re-ejecutar ningún tool_call nuevo — si esa llamada va sin tools bindeadas, algunos modelos (`gpt-oss-120b` confirmado) igual intentan invocar la tool de nuevo porque el prompt la sigue mencionando en texto, y Groq rechaza la respuesta con 400 ("Tool choice is none, but model called a tool"). Reusar este patrón para cualquier tool-calling multi-turn nuevo
- El microservicio Python de `chatbot` no tiene su propio control de acceso por usuario (vive en Nest) pero SÍ exige un secreto compartido (`CHATBOT_INTERNAL_TOKEN`, header `X-Internal-Token`) en TODAS sus rutas desde la auditoría del 2026-08-27/28 — fail-closed si la env var falta. `backend/.env` y `chatbot/.env` deben tener el MISMO valor. Cualquier endpoint nuevo del servicio Python queda cubierto automáticamente (dependency a nivel de `FastAPI(dependencies=[...])`, no por ruta)
- `PATCH /api/products/:id` YA NO acepta `stock` (removido de `UpdateProductDto` en la auditoría de seguridad) — el stock actual SOLO se ajusta vía `/api/stock/entries|sales` (CU06/CU07) o en la creación del producto. Cualquier UI que edite productos no debe mandar `stock` en el PATCH
