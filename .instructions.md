# Convenciones normativas de desarrollo — TP Ferretería/Pinturería

Este archivo define reglas **obligatorias** para todo cambio de código y documentación
técnica del proyecto. Es la fuente normativa principal para asistentes de IA
(OpenCode y Claude Code). Ante conflicto con cualquier otro documento, **prevalece este archivo**.

## 1) Arquitectura y estructura

- Backend NestJS modular: un módulo por dominio (`auth`, `users`, `products`,
  `categories`, `suppliers`, `stock`, `dashboard`, `chatbot`).
- Cada módulo sigue el patrón: `controller` → `service` → Prisma. Sin lógica de
  negocio en controllers.
- Recursos HTTP bajo `/api/<recurso>` en plural (`/api/products`). Health check en `/health`.
- Frontend React + Vite + TS: componentes por feature, llamadas a API centralizadas
  en `src/api/`.

## 2) Base de datos y Prisma

- Todo cambio de schema pasa por migración Prisma (`prisma migrate dev --name <nombre>`).
  Nunca editar la DB a mano.
- IDs: `uuid` generados por la DB (`@default(uuid())`).
- **Baja lógica de productos** (CU03): campo `deletedAt DateTime?`. Nunca borrado
  físico de productos ni de movimientos. Los listados filtran `deletedAt: null`.
- **Movimientos de stock son inmutables**: solo INSERT, nunca UPDATE/DELETE.
  El stock actual se mantiene en `Product.stock` y se ajusta en la misma transacción
  que crea el movimiento.

## 3) Transaccionalidad y concurrencia (CU06/CU07)

- Registrar venta o entrada de stock SIEMPRE dentro de `prisma.$transaction`.
- La venta valida disponibilidad DENTRO de la transacción con lectura que evite
  carreras (update condicional `stock >= cantidad` o lock explícito). Si no hay
  stock suficiente: `409 Conflict` con `{ "error": "Stock insuficiente" }` y
  ningún cambio persistido.
- Prohibido validar stock fuera de la transacción y después escribir.

## 4) Autenticación y autorización (CU01–CU03)

- JWT firmado con secreto en env (`JWT_SECRET`). Nunca hardcodear secretos.
- Passwords con `bcrypt` (salt rounds >= 10). Nunca loggear ni devolver hashes.
- Roles: `ADMIN` y `OPERARIO`. Autorización con Guards de Nest
  (`JwtAuthGuard` + `RolesGuard` + decorator `@Roles()`).
- Acceso sin token: `401`. Token válido pero rol insuficiente: `403`.
- Endpoints de gestión (usuarios, productos ABM, categorías, proveedores): solo `ADMIN`.
- Movimientos de stock: `OPERARIO` (y `ADMIN`). Búsqueda y dashboard: ambos roles.

## 5) Validación de entrada

- Todo endpoint de escritura usa DTOs con `class-validator` + `ValidationPipe`
  global (`whitelist: true`, `forbidNonWhitelisted: true`).
- Validar tipos, campos obligatorios, rangos (cantidades > 0, precios >= 0).
- Body vacío o con campos desconocidos: `400`.

## 6) Contrato de respuestas

- Éxito: `{ "data": ... }`. Listados paginables: `{ "data": [...], "meta": { total, page, pageSize } }`.
- Error: `{ "error": "mensaje claro" }` (+ `details` opcional en validaciones).
- Códigos: `200` lectura/actualización, `201` creación, `204` eliminación sin cuerpo,
  `400` validación, `401` sin autenticar, `403` sin permiso, `404` no encontrado,
  `409` conflicto de negocio (stock insuficiente, email duplicado).

## 7) Seguridad

- `helmet` activo, CORS con origen configurado por env (sin `*`), rate limiting
  en `/api/auth/login`.
- Sin stack traces ni detalles internos en producción (`NODE_ENV=production`).
- `.env` fuera de git; mantener `.env.example` actualizado.

## 8) Tests y verificación obligatoria

- Todo cambio funcional incluye tests (unit de services con Prisma mockeado,
  e2e de endpoints críticos: auth, roles 403, venta con stock insuficiente).
- Antes de marcar cualquier tarea como completa, ejecutar y pasar:
  1. `npx tsc --noEmit` (en backend y frontend)
  2. `npm run lint`
  3. `npm run test`
- Si algo falla: detenerse, explicar archivo/línea, proponer corrección. No avanzar.

## 9) SDD con OpenSpec

- Ninguna feature se implementa sin un change de OpenSpec con `proposal`, `design`,
  `specs` (escenarios WHEN/THEN) y `tasks` aprobados por el humano.
- El código implementa exactamente los escenarios de la spec. Si aparece un caso
  no cubierto, se actualiza la spec primero.
- Al terminar un change: verificación completa (§8) y luego archivar.

## 10) Módulo de IA

- **Sincronización del índice vectorial (CU03/CU10):** todo ABM de productos
  debe reflejarse en ChromaDB de inmediato. Implementar con eventos/hooks de
  NestJS (`ProductCreated/Updated/Deleted` -> listener que reindexa o elimina el
  documento) o un worker asíncrono con reintentos. Un producto dado de baja o
  inexistente NUNCA debe poder aparecer en resultados semánticos ni ser citado
  por el chatbot. La baja lógica quita el documento del índice.
- **Memoria del chatbot con control de tokens (CU09):** la memoria de
  conversación por usuario DEBE tener una estrategia de acotamiento (ventana de
  últimos N intercambios y/o summarization de lo antiguo) para no desbordar la
  ventana de contexto del LLM (Groq/Gemini/otro). Configurable por entorno.
  Prohibido pasar el historial completo sin límite.
- **Autonomía acotada del asistente (CU10):** el asistente puede usar function
  calling / tools para generar **borradores** de órdenes de compra en la base
  (`OrdenCompra` en estado `BORRADOR`). Esa autonomía NO viola la regla de oro:
  el LLM propone y crea el borrador, pero la confirmación de la orden y el
  ingreso de stock siguen siendo acciones humanas explícitas (CU06). Ninguna
  tool del asistente modifica stock ni confirma órdenes por sí sola.
